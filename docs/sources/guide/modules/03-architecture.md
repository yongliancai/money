# 03｜讓程式碼庫自己提供上下文

## 導向
工程規範不應只存在 Prompt 裡。專案的命名、目錄、模組、型別、API 契約與文件，應共同形成清楚且可檢查的結構。

## 判斷步驟

1. 找出重要邊界：前/後端、瀏覽器/伺服器、使用者/管理員、測試/正式環境、資料存取/業務邏輯。
2. 評估現有目錄與模組是否反映這些邊界；不得為了形式一致而改壞既有功能。
3. 畫出關鍵依賴方向：哪些模組允許引用，哪些不允許？先確認實際架構與例外。
4. 需要時使用語言適配工具落實邊界：ESLint、dependency-cruiser、import-linter、架構測試等均只是候選。
5. 對容易誤用的 API，優先比較：說明文件、單一封裝入口、型別限制、禁止使用。選擇最小有效措施。
6. 針對 UI/API/Agent 建立 **feature map**：功能名稱、入口、前置條件、主要步驟、狀態、測試方法；不必固定成某一工具格式。

## 驗證

至少一個刻意違反依賴規則的隔離案例應被檢查攔截；正常引用需通過。若進行目錄或 API 重構，原有整合/端到端測試需通過。

## 範例：Electron
renderer 不應直接引用 main 的權限程式碼，可採獨立目錄及 IPC 契約，由依賴檢查阻擋非法 import。這只是演講情境示例，其他專案須重新判斷邊界。
