# 04｜把糾正轉成可執行防護

## 根因到防護決策樹

**A. 能明確、低誤判地以靜態規則判定？** → 優先 Linter、型別或架構規則。

**B. 關係到輸入輸出或業務行為？** → 優先單元/整合/契約/回歸測試。

**C. 只在執行時才出現？** → 日誌、瀏覽器/E2E、效能監測、健康檢查。

**D. 屬於併發、狀態遷移或跨服務不變量？** → 狀態圖、屬性測試、模型檢查；嚴格必要時形式證明。

**E. 屬於語意品質或需求模糊？** → 評測集、人工裁決與明確的驗收準則；不可假裝完全決定性。

**F. 一次性低風險問題？** → 紀錄修復即可，避免無意義的永久規則。

## 防護建立工作單

1. 用可觀察證據描述原錯誤及重現方式。
2. 確認根因，而不是只記症狀。
3. 列出兩種以上候選防護（若只有一種，說明理由）。
4. 比較攔截能力、誤判、維護成本與執行時間。
5. 在已批准的隔離環境內實作最小方案。
6. 建立負例（必須失敗）與正例（必須通過）。
7. 記錄適用範圍、例外、負責維護位置與撤回條件。

## 不應自動做的事

- 為讓 CI 綠燈而關閉有效規則。
- 沒有證據就禁用所有註解、timer、hook 或特定語法。
- 因一次錯誤而建置與問題不相稱的大型工具鏈。
- 把 YAML 規則描述當成已啟用的 Linter 或自動測試。

模板：`templates/04-guardrail-record.yaml` 是資料範本，必須有實際程式/設定及測試執行器才能生效。
