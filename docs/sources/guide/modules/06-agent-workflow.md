# 06｜AI 自主工作循環與權限邊界

## 首次建置循環

`DISCOVER → AUDIT → DESIGN → WAIT_FOR_APPROVAL → IMPLEMENT → VERIFY → PERSIST → REPORT`

- 前三步只盤點與設計。
- **WAIT_FOR_APPROVAL 是硬性門檻**：對現有專案的首次建置與修改，使用者批准前停止。
- 授權後按小批次建立工具與規則，先保護核心路徑，再擴大覆蓋。
- 正式部署一律獨立徵得批准，不可將「自動修復」擴大解釋成「自動部署」。

## 日常開發循環

`READ_RULES → UNDERSTAND_TASK → PLAN_SCOPE → CHANGE → RUN_CHECKS → FIX → EVIDENCE → PR/REPORT`

- 在隔離分支工作；若專案沒有 Git，應至少保留可回復的變更紀錄。
- 嚴格限定修改範圍，避免無關重構。
- 需要運用終端機、瀏覽器或外部服務時，先確認當下權限。
- 發現規則衝突、破壞性風險、敏感資料、無法安全測試時，停止該危險步驟並回報。
- 可自行反覆修復**已批准範圍內的非破壞性問題**，但不應無限迴圈；反覆失敗就回報阻礙。

## 分類處置

| 行為 | 預設處置 |
|---|---|
| 唯讀盤點與提出計畫 | 可進行（依實際存取權限） |
| 建立/修改規範、程式、CI | 首次建置前需取得批准；之後依任務授權 |
| 本機隔離測試、修復 | 在已批准工作範圍內可自主 |
| 正式部署、正式資料變更 | 每次另行取得明確批准 |
| 刪除不可復原資料、讀取/傳送機密、擴權 | 另需專項授權及安全措施 |

## 交付
參照 `templates/05-evidence-report.md`，分開報告「已修改」「已執行驗證」「未驗證」「未部署」。不得把 PR 提交等同於部署。
