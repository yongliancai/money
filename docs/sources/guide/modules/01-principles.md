# 01｜工程哲學：先修開發循環，再擴大自動化

## 目的
學會 Lauren Tan《All Code Is Slop (Except Mine)》相關案例所強調的工程方法：提高代理工作的環境可信度，而不是提高對文字提示的依賴。此處以使用者提供的兩份演講摘要為依據；演講中的特定禁令、產量數據或工具名稱**不是普遍有效的規範或業界基準**。

## 八條可移植原則

1. **先修循環，後擴產能**：若當前開發迴圈常產生缺陷，更多 Agent 只會放大問題。先建立可重現的建置、測試與審查。
2. **程式碼庫如花園**：AI 易複製現有模式。清理會反覆擴散的反模式，提供清楚的好範例、API 契約與結構。
3. **決定性檢查勝過反覆提醒**：可以明確判定的要求，用 Lint、型別、架構檢查、測試或驗證工具；不是所有問題都能靠 Lint。
4. **讓正確路徑更容易**：對屢次誤用的高風險 API，考慮安全封裝、限制或（有證據時）禁止。不要照搬特定團隊對 `useEffect`、timer 或註解的禁令。
5. **目錄與依賴也是上下文**：資料夾名稱、模組方向、介面、依賴圖能同時引導 AI 與強化架構；遇到依賴違規時提供清楚錯誤訊息。
6. **真正執行程式**：靜態閱讀不足以證明 UI/服務行為；利用受控測試環境、瀏覽器、API、日誌與 feature map 驗證。
7. **驗證依風險而異**：一般邏輯使用單元/整合/屬性測試；高風險並行狀態可評估 state chart、TLA+ 或其他模型檢查；對特定可形式化性質才考慮 Lean 證明。
8. **證據驅動的審查**：截圖、影片、測試、效能數據、模型檢查結果可提高審查效率，但高風險改動不可只憑漂亮報告而免除適當人工審查。

## 反模式：不要這樣導入

- 一開始就自動合併與部署。
- 遇到 bug 只在提示詞末尾加「下次記得」。
- 把註解一律禁止、把某種語法一律禁止，不看專案實際情況。
- 產生一堆測試但未執行，或只驗證工具有安裝。
- 將「11,000 PR / 0.5% revert」當成自己的品質目標；這是演講描述的案例，不是可直接遷移的承諾。

## 工程決策測試
每次想加一條規則，問：有何具體錯誤？會重現嗎？是否可機器判定？誤判風險多高？現有工具可做到嗎？需要什麼測試來證明它有效？
