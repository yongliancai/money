# 08｜持續改善：讓每次修復留下資產

## 錯誤學習循環

`DETECT → REPRODUCE → ROOT_CAUSE → FIX → PREVENT → PROVE → RECORD`

- 寫出可重現案例；有時需要模擬或受控測試環境。
- 找到現有測試為何沒有攔截；調整適當的邊界或測試。
- 不是每次都加新規則；比較成本、誤報、風險與覆蓋率。
- 能加入回歸測試時，應確認其對錯誤版本能失敗。
- 以版本化紀錄保存原因與證據，避免無限累積失效規則。

## 成熟度（本手冊的導入模型，非演講原始分級）

1. **看得見**：專案有基本地圖、風險清單及可重現建置。
2. **攔得住**：基本檢查、關鍵測試和安全門檻能攔截已知問題。
3. **修得好**：AI 在隔離環境可自主修復，附驗證證據。
4. **驗得穩**：高頻低風險修改有成熟驗證；高風險修改仍需對應審查。
5. **持續改善**：錯誤、誤判、缺漏都持續反饋至規則與測試。

成熟度不等於允許自動部署。**正式部署始終需使用者批准。**

## 觀察指標

建議追蹤：回歸缺陷數、缺陷逃逸率、重要檢查覆蓋範圍、測試誤報/不穩定率、驗證耗時、回退率、平均修復時間、人工審查成本。不以 PR 量作為唯一目標，且不要在沒有基準資料時聲稱改善。

## 定期整理
移除過時的例外及無效測試、合併重複規範、確認依賴工具仍可用；修改強制規則前先提出原因與驗證計畫。
