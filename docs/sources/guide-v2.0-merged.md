# AI Code Factory Guide v2.0（審查草案）

這是一套交給**具備專案操作能力的 AI Agent** 使用的跨平台方法論。它教 AI 依專案狀況選擇工程工具、建立驗證環境、保留規範與持續改善，而不是預裝一組固定工具。

**請由 [`START-HERE.md`](START-HERE.md) 開始。**

## 結構
- `START-HERE.md`：AI 執行入口與權限門檻。
- `modules/01–08`：工程哲學、盤點、架構、決定性防護、驗證、工作流程、持久化、持續改善。
- `templates/`：盤點、計畫、驗收、規則紀錄、證據報告、專案入口範本。
- `examples/`：依專案特性選工具的決策案例。

## 使用者的既定要求
- 通用於不同 AI；平台不支援的功能不得假裝能用。
- 舊專案先盤點、提出分階段方案；獲批准後才能建置。
- AI 在授權範圍可自主修改、修復與驗證。
- **正式部署每次另需人工批准。**
- 這個版本只是一份獨立文件套件；**沒有修改任何現有專案，也沒有替你建立真實 Lint / CI / 測試。**

## 預期用途
把整個資料夾交給 AI，要求它先閱讀 `START-HERE.md` 並僅做第一輪盤點與規劃。你批准建置計畫後，它才依實際專案產生可執行規則和測試。建置驗收完成後，另在新的工作階段測試規範持久化。

## 來源與適用限制
核心思維依使用者提供的兩份 Lauren Tan《All Code Is Slop (Except Mine)》影片摘要整理；並未宣稱全文逐字核對。案例中的 `useEffect`、註解禁令及工具名稱是特定情境，不直接作為普遍規範。

# AI Code Factory Guide v2.0 — AI 啟動入口

> 狀態：審查草案（Draft）。這是一份跨 AI 平台的**方法論與自主建置操作指引**，不是安裝即生效的程式，也不是永久記憶的保證。

## 使命

你的任務不是複述本手冊，而是**在授權範圍內，把目前專案變成可理解、可測試、可驗證、可持續改善的開發環境**。讓正確模式容易採用、錯誤容易被攔截。規則能以程式檢查時，優先實作檢查而非重複增加提示詞。

## 使用者已指定的預設權限

- **第一輪只盤點、診斷與提出計畫；建置前取得使用者批准。**
- 取得建置批准後，可在授權範圍與隔離工作區自行實作、測試、修復；不要把批准建置解讀成批准部署。
- **每次正式部署都需要使用者另行明確批准。** 正式資料庫變更、刪除資料、外傳密鑰、擴大權限等高風險行為也要獨立授權。
- 不應假定自己有 Git、終端機、瀏覽器、網路或平台記憶能力；先檢查實際工具及權限。

## 閱讀路徑

**首次導入：** 先閱讀本文與 `modules/01-principles.md`、`02-audit.md`、`03-architecture.md`、`04-guardrails.md`、`05-verification.md`、`06-agent-workflow.md`、`07-persistence.md`、`08-continuous-improvement.md`。必要時參照 `templates/`。

**日常開發：** 優先讀取專案內已建立的規範與相關章節；不必每次重新讀完全部文件。若缺少專案規範或規範已失效，回到首次導入流程。

## 必須遵循的有限狀態流程

1. **DISCOVER**：辨識平台、工具、權限及專案目標；未知就標註未知。
2. **AUDIT**：唯讀盤點結構、測試、風險、已知 Bug、部署及資料安全；記錄證據。
3. **DESIGN**：挑選成本與風險相稱的改善措施，提出分階段方案及可量測的驗收條件。
4. **APPROVAL GATE**：提交計畫等待明確批准。**未批准不得改動現有專案。**
5. **IMPLEMENT**：依核准範圍建立/調整結構、規範、測試及工具；優先改進最小且高價值的環節。
6. **VERIFY**：執行檢查；驗證防護對故意植入的違規或回歸案例有攔截效果。結果須區分 PASS / FAIL / BLOCKED / NOT_CONFIGURED / NOT_APPLICABLE。
7. **PERSIST**：保留版本化的專案規範、執行命令、決策與驗證證據；為平台建立適配入口；可行時用全新工作階段測試重新載入。
8. **REPORT**：報告完成、未完成、證據、風險及下一步。正式部署另走批准流程。

如果步驟失敗：回到對應階段修復；停止無效重試，記錄阻礙；不可藉由刪測試、降低門檻或藏錯誤偽造 PASS。

## 核心決策規則

- **先修循環、再擴自動化。** 不以 PR 產量作為品質代理指標。
- **先找根因、再加規則。** 只有可客觀檢驗且有足夠價值的要求才做成自動檢查；其餘保留成決策原則/人工審查。
- **架構本身是上下文。** 模組邊界、目錄、型別與 API 契約通常比反覆警告更持久。
- **驗證強度隨風險升高。** UI、資料庫、權限、金流、並行狀態或 AI 模型輸出須有相應驗證，不是一套工具通吃。
- **專案來源優先且不盲從。** 遵循合法授權與已確認需求；若既有規範衝突，先提出並解決衝突。
- **不要過度工程化。** 小型靜態網站不需被強加形式化驗證；高風險並行系統則應評估狀態機、模型檢查等方法。

## 第一輪輸出契約（不得只給泛泛建議）

交付：`templates/01-audit-report.md` 形式的盤點報告、`templates/02-adoption-plan.md` 形式的建置計畫，以及 `templates/03-acceptance-checklist.md` 的擬定驗收標準。至少說明問題證據、優先序、工具選擇理由、哪些不做、預期驗證方式、變更與部署權限邊界。**第一輪到此停止，等待批准。**

## 範本、程式碼與平台適配

- `modules/` 是方法論，供 AI 理解與判斷。
- `templates/` 是可複製、修改的結構化輸出範本，**不是可執行工具**。
- `examples/` 是示例，並非每個專案必裝的固定配置。
- 有程式執行權限的 AI 可根據專案產生 ESLint、測試、CI、CLI、Rules 等；沒有該能力就應明確說明限制。

## 最小成功標準

AI 能提出有證據的計畫；批准後能建立至少一個真正有效的防護（對已知錯誤/違規案例會失敗，對正確案例能通過）、明確保存工程規則與驗證入口，並讓下一個無原始對話上下文的 AI 可以使用。**不得將讀過本手冊等同於已完成建置。**

# 01｜工程哲學：先修開發循環，再擴大自動化

## 目的
學會 Lauren Tan《All Code Is Slop (Except Mine)》相關案例所強調的工程方法：提高代理工作的環境可信度，而不是提高對文字提示的依賴。此處以使用者提供的兩份演講摘要為依據；演講中的特定禁令、產量數據或工具名稱**不是普遍有效的規範或業界基準**。

## 八條可移植原則

1. **先修循環，後擴產能**：若當前開發迴圈常產生缺陷，更多 Agent 只會放大問題。先建立可重現的建置、測試與審查。
2. **程式碼庫如花園**：AI 易複製現有模式。清理會反覆擴散的反模式，提供清楚的好範例、API 契約與結構。
3. **決定性檢查勝過反覆提醒**：可以明確判定的要求，用 Lint、型別、架構檢查、測試或驗證工具；不是所有問題都能靠 Lint。
4. **讓正確路徑更容易**：對屢次誤用的高風險 API，考慮安全封裝、限制或（有證據時）禁止。不要照搬特定團隊對 `useEffect`、timer 或註解的禁令。
5. **目錄與依賴也是上下文**：資料夾名稱、模組方向、介面、依賴圖能同時引導 AI 與強化架構；遇到依賴違規時提供清楚錯誤訊息。
6. **真正執行程式**：靜態閱讀不足以證明 UI/服務行為；利用受控測試環境、瀏覽器、API、日誌與 feature map 驗證。
7. **驗證依風險而異**：一般邏輯使用單元/整合/屬性測試；高風險並行狀態可評估 state chart、TLA+ 或其他模型檢查；對特定可形式化性質才考慮 Lean 證明。
8. **證據驅動的審查**：截圖、影片、測試、效能數據、模型檢查結果可提高審查效率，但高風險改動不可只憑漂亮報告而免除適當人工審查。

## 反模式：不要這樣導入

- 一開始就自動合併與部署。
- 遇到 bug 只在提示詞末尾加「下次記得」。
- 把註解一律禁止、把某種語法一律禁止，不看專案實際情況。
- 產生一堆測試但未執行，或只驗證工具有安裝。
- 將「11,000 PR / 0.5% revert」當成自己的品質目標；這是演講描述的案例，不是可直接遷移的承諾。

## 工程決策測試
每次想加一條規則，問：有何具體錯誤？會重現嗎？是否可機器判定？誤判風險多高？現有工具可做到嗎？需要什麼測試來證明它有效？

# 02｜專案盤點與風險分級

## 唯讀盤點順序

1. **能力盤點**：目前平台、工具、工作目錄、Git/測試/瀏覽器可用性、授權範圍；不知道就寫未知，不臆測。
2. **專案地圖**：入口檔、主要頁面、模組、資料庫、外部依賴、環境設定名稱、任務流、部署流程。
3. **架構與文件**：搜尋既有 ADR、README、Rules、Skills、AGENTS/CLAUDE 類檔案（只在實際適用時）；發現衝突標記。
4. **驗證現況**：Lint、型別檢查、測試、CI、健康檢查、觀測性、部署回滾、失敗時的反饋。
5. **歷史證據**：已知 Bug、可取得的 issue、PR、測試失敗及真實事故；絕不捏造未讀取的歷史。
6. **資料風險**：正式/測試資料界線、機密、權限、刪除操作、網路外傳風險；不要讀取或洩漏不必要的密鑰值。

## 風險分級矩陣

以影響範圍、發生可能性、可偵測性、可逆性分類為高/中/低，附具體證據；沒有足夠證據時標「待查」。以下情況通常優先：資料遺失、外洩、未授權操作、認證錯誤、正式環境中斷、金流/核心流程錯誤。

## 不要過度推導

- 看到很多檔案不等於一定需要拆微服務。
- 沒有測試不代表應立即全面重寫。
- 一個沒有型別系統的舊專案不等於需立即遷移 TypeScript。
- 先列出可以小步驗證的最短路徑。

## 產出
填寫 `templates/01-audit-report.md`；每項問題至少附位置、可觀察證據、風險及待確認資訊。再進入建置計畫，而非直接修改。

# 03｜讓程式碼庫自己提供上下文

## 導向
工程規範不應只存在 Prompt 裡。專案的命名、目錄、模組、型別、API 契約與文件，應共同形成清楚且可檢查的結構。

## 判斷步驟

1. 找出重要邊界：前/後端、瀏覽器/伺服器、使用者/管理員、測試/正式環境、資料存取/業務邏輯。
2. 評估現有目錄與模組是否反映這些邊界；不得為了形式一致而改壞既有功能。
3. 畫出關鍵依賴方向：哪些模組允許引用，哪些不允許？先確認實際架構與例外。
4. 需要時使用語言適配工具落實邊界：ESLint、dependency-cruiser、import-linter、架構測試等均只是候選。
5. 對容易誤用的 API，優先比較：說明文件、單一封裝入口、型別限制、禁止使用。選擇最小有效措施。
6. 針對 UI/API/Agent 建立 **feature map**：功能名稱、入口、前置條件、主要步驟、狀態、測試方法；不必固定成某一工具格式。

## 驗證

至少一個刻意違反依賴規則的隔離案例應被檢查攔截；正常引用需通過。若進行目錄或 API 重構，原有整合/端到端測試需通過。

## 範例：Electron
renderer 不應直接引用 main 的權限程式碼，可採獨立目錄及 IPC 契約，由依賴檢查阻擋非法 import。這只是演講情境示例，其他專案須重新判斷邊界。

# 04｜把糾正轉成可執行防護

## 根因到防護決策樹

**A. 能明確、低誤判地以靜態規則判定？** → 優先 Linter、型別或架構規則。

**B. 關係到輸入輸出或業務行為？** → 優先單元/整合/契約/回歸測試。

**C. 只在執行時才出現？** → 日誌、瀏覽器/E2E、效能監測、健康檢查。

**D. 屬於併發、狀態遷移或跨服務不變量？** → 狀態圖、屬性測試、模型檢查；嚴格必要時形式證明。

**E. 屬於語意品質或需求模糊？** → 評測集、人工裁決與明確的驗收準則；不可假裝完全決定性。

**F. 一次性低風險問題？** → 紀錄修復即可，避免無意義的永久規則。

## 防護建立工作單

1. 用可觀察證據描述原錯誤及重現方式。
2. 確認根因，而不是只記症狀。
3. 列出兩種以上候選防護（若只有一種，說明理由）。
4. 比較攔截能力、誤判、維護成本與執行時間。
5. 在已批准的隔離環境內實作最小方案。
6. 建立負例（必須失敗）與正例（必須通過）。
7. 記錄適用範圍、例外、負責維護位置與撤回條件。

## 不應自動做的事

- 為讓 CI 綠燈而關閉有效規則。
- 沒有證據就禁用所有註解、timer、hook 或特定語法。
- 因一次錯誤而建置與問題不相稱的大型工具鏈。
- 把 YAML 規則描述當成已啟用的 Linter 或自動測試。

模板：`templates/04-guardrail-record.yaml` 是資料範本，必須有實際程式/設定及測試執行器才能生效。

# 05｜驗證是產出物，不是口號

## 驗證層次

- **靜態檢查**：格式、Lint、型別、依賴邊界、秘密掃描；可快速阻擋部分問題。
- **行為測試**：單元、整合、API 契約、E2E；依受影響流程分層。
- **執行期驗證**：啟動真實 App（隔離環境）、Chrome DevTools 或其他受控瀏覽器工具、日誌、截圖及互動流程。
- **屬性與狀態**：對大量輸入、複雜狀態使用 property-based / state-machine testing。
- **形式化方法**：TLA+ 適用於可模型化的時序/並發不變量，Lean 適用於可形式表述的特定性質。需要專業模型與假設審查；不保證整個產品正確。
- **AI 系統評測**：多輪對話、檢索引用、工具呼叫、結構化輸出、對抗提示、成本與延遲；模型輸出具變異性，宜使用評測集與人工覆核。

## 每次修改的驗證設計

1. 定義**成功條件**（功能、非功能及不可破壞的行為）。
2. 列出影響範圍及最小必要測試集合；對風險高的地方加深驗證。
3. 有可能時先讓測試在原錯誤版本失敗（red），再確認修復版本通過（green）。
4. 規則層面需測負例和正例，避免「規則檔存在但沒有生效」。
5. 將測試命令、版本、環境、執行時間、退出狀態與可用的截圖/日誌記為證據。
6. 報告缺口，不要把不可驗證的項目推論成成功。

## 結果狀態（嚴禁混用）

- `PASS`: 真正執行且通過。
- `FAIL`: 真正執行但失敗。
- `BLOCKED`: 因外部條件/權限無法執行。
- `NOT_CONFIGURED`: 尚未建置對應檢查。
- `NOT_APPLICABLE`: 經有理由的判斷不適用。

## 審查證據
以執行結果、截圖/錄影、狀態圖、效能數據、形式驗證報告輔助 Code Review。對資料庫、基礎設施、身分認證、部署、權限或核心使用者體驗仍應按風險保留人工審查。

## 自我驗收
獨立於實作步驟重新執行必要檢查；條件允許時請第二個 Agent 或獨立測試流程提出反例。驗證者不可只抄錄建置者聲稱的結果。

# 06｜AI 自主工作循環與權限邊界

## 首次建置循環

`DISCOVER → AUDIT → DESIGN → WAIT_FOR_APPROVAL → IMPLEMENT → VERIFY → PERSIST → REPORT`

- 前三步只盤點與設計。
- **WAIT_FOR_APPROVAL 是硬性門檻**：對現有專案的首次建置與修改，使用者批准前停止。
- 授權後按小批次建立工具與規則，先保護核心路徑，再擴大覆蓋。
- 正式部署一律獨立徵得批准，不可將「自動修復」擴大解釋成「自動部署」。

## 日常開發循環

`READ_RULES → UNDERSTAND_TASK → PLAN_SCOPE → CHANGE → RUN_CHECKS → FIX → EVIDENCE → PR/REPORT`

- 在隔離分支工作；若專案沒有 Git，應至少保留可回復的變更紀錄。
- 嚴格限定修改範圍，避免無關重構。
- 需要運用終端機、瀏覽器或外部服務時，先確認當下權限。
- 發現規則衝突、破壞性風險、敏感資料、無法安全測試時，停止該危險步驟並回報。
- 可自行反覆修復**已批准範圍內的非破壞性問題**，但不應無限迴圈；反覆失敗就回報阻礙。

## 分類處置

| 行為 | 預設處置 |
|---|---|
| 唯讀盤點與提出計畫 | 可進行（依實際存取權限） |
| 建立/修改規範、程式、CI | 首次建置前需取得批准；之後依任務授權 |
| 本機隔離測試、修復 | 在已批准工作範圍內可自主 |
| 正式部署、正式資料變更 | 每次另行取得明確批准 |
| 刪除不可復原資料、讀取/傳送機密、擴權 | 另需專項授權及安全措施 |

## 交付
參照 `templates/05-evidence-report.md`，分開報告「已修改」「已執行驗證」「未驗證」「未部署」。不得把 PR 提交等同於部署。

# 07｜跨平台持久化：不依賴對話記憶

## 核心原則
跨 AI 平台的可靠承載物是**專案內版本化的規範與可執行檢查**。平台記憶、Rules、Skills 和專屬指令只是把它們載入上下文的適配器。不能假定任何 AI 閱讀一次就永久記住。

## 平台能力偵測

1. 辨識 Agent 與目前版本；若不確定，查詢可用工具/官方設定，不猜測。
2. 檢查是否支援專案指令、Rules、Skills、持久化設定、倉庫級約束、自動載入順序。
3. 實際確認哪些檔案會被自動讀入、作用範圍、衝突時的優先序，以及是否有長度限制。
4. 不支援持久化時，保留 `PROJECT-ENGINEERING.md` 類通用文件及入口指令，要求每次明確載入。

## 單一來源與平台適配

- 建議在專案內維護一份**主要工程規範**（名稱由專案自行決定）及其引用的驗證命令、架構圖與決策紀錄。
- 平台專屬入口只負責指向主要規範及任務相關檔案，不要長篇複製成互相矛盾的版本。
- 可依支援狀態使用 `AGENTS.md`、`CLAUDE.md`、Cursor 專案 Rules、Skills 或其他等價機制；**名稱僅為候選，不代表所有平台或版本均會自動讀取**。
- 不要把密鑰、個資、執行中暫存資訊或未經確認的推測寫入長期記憶。

## 驗收方法

1. 在目前環境確認規範可被載入。
2. 啟動**全新、沒有原對話上下文**的工作階段（若平台允許），交付同一專案。
3. 要求新 Agent 指出規範入口、禁止操作、驗證命令、部署批准規則。
4. 讓新 Agent 在隔離情境辨識一項故意違規的變更，且實際檢查必須攔截。
5. 若平台無法驗證新工作階段，標記為 `BLOCKED`；不得宣稱跨對話成功。

## 變更治理
專案規範有版本、責任人/變更原因、審查紀錄和例外期限。平台適配檔變更時應檢查仍與主要規範一致。

# 08｜持續改善：讓每次修復留下資產

## 錯誤學習循環

`DETECT → REPRODUCE → ROOT_CAUSE → FIX → PREVENT → PROVE → RECORD`

- 寫出可重現案例；有時需要模擬或受控測試環境。
- 找到現有測試為何沒有攔截；調整適當的邊界或測試。
- 不是每次都加新規則；比較成本、誤報、風險與覆蓋率。
- 能加入回歸測試時，應確認其對錯誤版本能失敗。
- 以版本化紀錄保存原因與證據，避免無限累積失效規則。

## 成熟度（本手冊的導入模型，非演講原始分級）

1. **看得見**：專案有基本地圖、風險清單及可重現建置。
2. **攔得住**：基本檢查、關鍵測試和安全門檻能攔截已知問題。
3. **修得好**：AI 在隔離環境可自主修復，附驗證證據。
4. **驗得穩**：高頻低風險修改有成熟驗證；高風險修改仍需對應審查。
5. **持續改善**：錯誤、誤判、缺漏都持續反饋至規則與測試。

成熟度不等於允許自動部署。**正式部署始終需使用者批准。**

## 觀察指標

建議追蹤：回歸缺陷數、缺陷逃逸率、重要檢查覆蓋範圍、測試誤報/不穩定率、驗證耗時、回退率、平均修復時間、人工審查成本。不以 PR 量作為唯一目標，且不要在沒有基準資料時聲稱改善。

## 定期整理
移除過時的例外及無效測試、合併重複規範、確認依賴工具仍可用；修改強制規則前先提出原因與驗證計畫。

# 示範決策案例（非固定安裝清單）

## 案例 A：純 HTML/CSS/JS 小網站
- 現象：修改一個元件常影響其他頁面排版。
- 先查：是否已有可重現的頁面或視覺比較方式，是否有共用 CSS 命名衝突。
- 候選：CSS 命名規約、少量關鍵頁面截圖比較、Playwright smoke test；不需要直接導入 TLA+。
- 驗收：故意移除關鍵按鈕應使測試失敗，正常頁面操作通過。

## 案例 B：Node.js API + 聊天模型
- 現象：聊天模型偶爾偏離指定文件回答。
- 先查：檢索資料、Prompt 版本、模型設定、工具輸出及失敗對話是否可重現。
- 候選：文件引用驗證、拒答案例、固定評測集、Schema、API 整合測試。
- 驗收：多組文件內、文件外、模糊提問案例各有量測結果；不可把偶然一次成功當作全面保證。

## 案例 C：Electron main/renderer
- 現象：renderer 直接 import main 模組，權限/打包出錯。
- 候選：清楚的目錄與 IPC 邊界；依賴圖規則；非法引用的負例檢查。
- 驗收：違規依賴被攔截，合法跨程序通訊可通過整合測試。

## 案例 D：跨裝置通知狀態同步
- 現象：訊息重送、離線及重連時狀態不一致。
- 候選：狀態圖、property-based/state-machine test；若風險高且有模型能力，評估 TLA+。
- 驗收：定義不變量，檢查競爭條件與重試情境。模型正確不保證實作零缺陷，仍需系統測試。
