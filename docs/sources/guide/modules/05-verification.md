# 05｜驗證是產出物，不是口號

## 驗證層次

- **靜態檢查**：格式、Lint、型別、依賴邊界、秘密掃描；可快速阻擋部分問題。
- **行為測試**：單元、整合、API 契約、E2E；依受影響流程分層。
- **執行期驗證**：啟動真實 App（隔離環境）、Chrome DevTools 或其他受控瀏覽器工具、日誌、截圖及互動流程。
- **屬性與狀態**：對大量輸入、複雜狀態使用 property-based / state-machine testing。
- **形式化方法**：TLA+ 適用於可模型化的時序/並發不變量，Lean 適用於可形式表述的特定性質。需要專業模型與假設審查；不保證整個產品正確。
- **AI 系統評測**：多輪對話、檢索引用、工具呼叫、結構化輸出、對抗提示、成本與延遲；模型輸出具變異性，宜使用評測集與人工覆核。

## 每次修改的驗證設計

1. 定義**成功條件**（功能、非功能及不可破壞的行為）。
2. 列出影響範圍及最小必要測試集合；對風險高的地方加深驗證。
3. 有可能時先讓測試在原錯誤版本失敗（red），再確認修復版本通過（green）。
4. 規則層面需測負例和正例，避免「規則檔存在但沒有生效」。
5. 將測試命令、版本、環境、執行時間、退出狀態與可用的截圖/日誌記為證據。
6. 報告缺口，不要把不可驗證的項目推論成成功。

## 結果狀態（嚴禁混用）

- `PASS`: 真正執行且通過。
- `FAIL`: 真正執行但失敗。
- `BLOCKED`: 因外部條件/權限無法執行。
- `NOT_CONFIGURED`: 尚未建置對應檢查。
- `NOT_APPLICABLE`: 經有理由的判斷不適用。

## 審查證據
以執行結果、截圖/錄影、狀態圖、效能數據、形式驗證報告輔助 Code Review。對資料庫、基礎設施、身分認證、部署、權限或核心使用者體驗仍應按風險保留人工審查。

## 自我驗收
獨立於實作步驟重新執行必要檢查；條件允許時請第二個 Agent 或獨立測試流程提出反例。驗證者不可只抄錄建置者聲稱的結果。
