# ADR-05/06｜保守提醒的產品取捨（待決）

已確認：忘記記帳時希望主動提醒；未知狀態寧漏勿誤；每天最多一則正式提醒；前一天不補發。無法透過 Web Push 得知未同步的本機操作，因此不能同時保證「全天沒開也提醒」與「不會誤提醒」。

| 情境           | 可驗證處理                                                              | 必然取捨                                                                    |
| -------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 全天未開 App   | 無今日可信快照 → unknown → 不 claim                                     | 會漏提醒；不可套用昨天未完成推論今天                                        |
| 離線新增       | 帳本、activity、outbox 原子寫入；重連同步                               | 後端此前的未完成快照在有效期內仍可能誤提醒                                  |
| 新增後刪除     | 本機剩餘今日 activity 為空 → 新 revision completed=false                | 已發送的日 claim 不釋放；不能因刪除再送第二則                               |
| 裝置時區改變   | 明示 IANA 設定；更改設定 revision，使舊時區狀態失效；本機重新計算活動日 | 裝置自動偵測時區與使用者保存設定可能不同，應提醒重新核對；不能用 UTC 截日期 |
| 延遲／亂序事件 | eventId 冪等、較小 revision 不覆蓋；freshness 使用 occurredAt           | 收到舊事件不能把它當成剛發生，也不重送前一天                                |
| 推播結果未知   | claim 先於 send，失敗不盲目重試                                         | 保證至多一次嘗試優先，無法保證送達                                          |

候選策略：最近當日狀態在 `maxAgeSeconds` 內、未完成、已過設定時間及 `debounceSeconds` 才有資格。這兩個值沒有產品批准；程式接受可注入 policy 供隔離測試，預設 `null` 並回傳 policy_pending。測試值 300／10 秒只是 fixture，未寫入產品預設。

候選替代方案：只在剛同步後提醒（更保守、容易漏）；或放寬到全天未知也提醒（更積極，但改變已選保守政策，未採用）。人工批准有效期與延遲、取得 HTTPS／實機證據之前，正式通知維持停用。

若啟用有限有效期，必須承認同步後離線修改的時間窗，不能宣稱零誤提醒。補發只可在同一當地日期且與常規共用日 claim；跨日永不補發。狀態指標分 accepted（供應商接受）、failed_or_unknown、completed、stale、unknown、policy_pending、already_claimed，沒有「已送達」推論。
