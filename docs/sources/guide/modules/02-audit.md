# 02｜專案盤點與風險分級

## 唯讀盤點順序

1. **能力盤點**：目前平台、工具、工作目錄、Git/測試/瀏覽器可用性、授權範圍；不知道就寫未知，不臆測。
2. **專案地圖**：入口檔、主要頁面、模組、資料庫、外部依賴、環境設定名稱、任務流、部署流程。
3. **架構與文件**：搜尋既有 ADR、README、Rules、Skills、AGENTS/CLAUDE 類檔案（只在實際適用時）；發現衝突標記。
4. **驗證現況**：Lint、型別檢查、測試、CI、健康檢查、觀測性、部署回滾、失敗時的反饋。
5. **歷史證據**：已知 Bug、可取得的 issue、PR、測試失敗及真實事故；絕不捏造未讀取的歷史。
6. **資料風險**：正式/測試資料界線、機密、權限、刪除操作、網路外傳風險；不要讀取或洩漏不必要的密鑰值。

## 風險分級矩陣

以影響範圍、發生可能性、可偵測性、可逆性分類為高/中/低，附具體證據；沒有足夠證據時標「待查」。以下情況通常優先：資料遺失、外洩、未授權操作、認證錯誤、正式環境中斷、金流/核心流程錯誤。

## 不要過度推導

- 看到很多檔案不等於一定需要拆微服務。
- 沒有測試不代表應立即全面重寫。
- 一個沒有型別系統的舊專案不等於需立即遷移 TypeScript。
- 先列出可以小步驗證的最短路徑。

## 產出
填寫 `templates/01-audit-report.md`；每項問題至少附位置、可觀察證據、風險及待確認資訊。再進入建置計畫，而非直接修改。
